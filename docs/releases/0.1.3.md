# Mirante 0.1.3

Mirante 0.1.3 adds line styling during dataset publication and a bundled Google
OIDC login extension backed by GeoNode's standard social-account provider.

## Dataset styling

- Line datasets can now receive a configurable stroke color and width during
  publication.
- Styling remains optional and preserves GeoNode's default behavior when no
  values are selected.

## Google login

- The official distribution includes an enabled-by-default Google login
  extension using GeoNode 5.1.0's generic OpenID Connect provider.
- Authentication secrets and provider accounts remain entirely in GeoNode;
  Mirante receives only the resulting Django session.
- The sign-in action includes the Google icon and the top-right account controls
  adapt to long display names.
- The local development stack now presents Mirante and GeoNode browser routes
  on `localhost:5173`, preventing successful OAuth logins from falling back to
  a GeoNode profile page.

Production operators must enable the GeoNode OIDC provider, configure a Google
OAuth web application and attach the matching Social application to the active
Django Site. Local signup can remain closed while social signup is controlled
independently through `ACCOUNT_OPEN_SOCIALSIGNUP`. Follow the versioned
[Google OIDC guide](https://github.com/barbosaneto/mirante/blob/v0.1.3/docs/google-oidc.md)
before exposing the login button.

## Installation

New installations should download the five deployment assets attached to the
[Mirante 0.1.3 release](https://github.com/barbosaneto/mirante/releases/tag/v0.1.3),
verify `SHA256SUMS`, create `.env` from `mirante.env.example`, and follow the
[production guide](https://github.com/barbosaneto/mirante/blob/v0.1.3/docs/deployment.md).

Existing installations can deploy the frontend by setting
`MIRANTE_VERSION=0.1.3`, pulling, and recreating the `mirante` service. Enabling
Google login also changes GeoNode configuration and requires recreating Django
and Celery after the new OIDC environment values are added. No persistent
volumes need to be removed.

AMD64 continues to use official upstream runtime images. ARM64 deployments
must continue to pass `compose.arm64.yml` to validation and every Compose
command.

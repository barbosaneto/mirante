# Mirante 0.1.2

Mirante 0.1.2 improves production interoperability with vanilla GeoNode and
adds direct layer-order control plus two keyless OpenFreeMap base maps.

## Map improvements

- Drag active datasets in the left panel to change their stacking order on the
  map. Saved GeoNode maps preserve that order.
- Choose OpenStreetMap, OpenFreeMap Liberty, or OpenFreeMap Dark without an API
  key. CARTO Dark Matter is no longer included.

## GeoNode and GeoServer fixes

- GeoServer administration links now open `/geoserver/web/` instead of the
  GeoWebCache landing page.
- Celery starts with the current Compose environment after Django becomes
  healthy, avoiding stale GeoServer credentials during dataset publication.
- GeoWebCache REST remains in its separate context so uploaded SLD styles can
  be assigned to new layers.
- Production proxy limits account for GeoNode's duplicated ZIP upload fields,
  preventing valid archives below the configured 100 MiB file limit from being
  rejected with HTTP 413.
- Deployment guidance now covers GeoNode-to-GeoServer authentication failures
  and links to the public instance at [mirantegeo.org](https://mirantegeo.org).

## Installation

New installations should download the five deployment assets attached to the
[Mirante 0.1.2 release](https://github.com/barbosaneto/mirante/releases/tag/v0.1.2),
verify `SHA256SUMS`, create `.env` from `mirante.env.example`, and follow the
[production guide](https://github.com/barbosaneto/mirante/blob/v0.1.2/docs/deployment.md).

Existing installations can deploy the frontend improvements by setting
`MIRANTE_VERSION=0.1.2`, pulling, and recreating only the `mirante` service.
That operation does not update previously downloaded Compose or environment
files. Operators who have not already applied the Celery, GeoWebCache, and
upload-limit corrections must compare their private deployment with the new
`compose.yml` and `mirante.env.example` assets before restarting affected
services. Back up persistent data before changing the complete stack.

AMD64 continues to use official upstream runtime images. ARM64 deployments
must continue to pass `compose.arm64.yml` to validation and every Compose
command.

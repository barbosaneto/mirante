# Authentication

Mirante authenticates against an unmodified GeoNode 5.1.0 instance using its standard Django session.

## Request flow

1. Fetch `GET /account/login/` and read the CSRF token generated by GeoNode.
2. Submit the username and password to `POST /account/ajax_login` as form data.
3. Let the browser retain the HttpOnly Django session cookie.
4. Read the current session identity from `GET /api/v2/userinfo/`.
5. Fetch the authenticated profile from the API V2 users resource.
6. Fetch a new CSRF token and submit `POST /account/logout/` to end the session.

Passwords, session cookies, CSRF values, and access tokens are never stored by application code. The session cookie remains HttpOnly and GeoNode is consulted on every application startup. The session information response is marked `no-store`; Mirante reads only its numeric subject and deliberately ignores the access token included by GeoNode.

## Required access

Set `VITE_REQUIRE_AUTHENTICATION=true` to prevent the map, catalogue, and tools
from loading until GeoNode confirms an authenticated session. The default is
`false`, which preserves anonymous browsing while keeping protected actions
unavailable.

This setting protects the Mirante interface, not GeoNode endpoints. A private
deployment must also remove anonymous view and download permissions from its
resources and configure GeoNode's defaults accordingly.

## Social and institutional login

GeoNode uses `django-allauth` for social authentication. Provider credentials,
callback URLs, and secrets are configured only in GeoNode. Mirante extensions
register presentation metadata and the relative GeoNode login path. For
example, GeoNode 5.1.0 can expose Google through its built-in generic OIDC
provider:

```ts
import { defineExtension } from "@mirante/sdk";

export const institutionalLogin = defineExtension({
  id: "institutional-login",
  authenticationProviders: [
    {
      id: "google",
      labelKey: "providers.google",
      loginPath: "/account/geonode_openid_connect/login/?process=login",
    },
  ],
  translations: {
    en: { providers: { google: "Continue with Google" } },
    "pt-BR": { providers: { google: "Continuar com Google" } },
  },
});
```

The registered button navigates to GeoNode, includes a return URL to the
current Mirante page, and lets GeoNode complete the provider flow. On return,
the same session restoration path recognizes the user. Provider paths must be
same-origin absolute paths; external URLs are rejected by the registry.

The official distribution enables this Google OIDC provider as a reference
extension by default. Configure the provider and its operator-owned credentials
in GeoNode before exposing the login flow. Set
`VITE_GOOGLE_OIDC_ENABLED=false` in development or
`MIRANTE_GOOGLE_OIDC_ENABLED=false` in production to hide the button. See
[Google OIDC](google-oidc.md) for the complete procedure.

## Deployment

The recommended topology exposes Mirante and the GeoNode routes through the same public origin. The development server proxies `/account` and `/api` to GeoNode. A production reverse proxy must preserve the same routes and cookies.

Cross-origin cookie authentication is not enabled automatically. Deployments that choose separate origins must configure GeoNode, HTTPS, cookies, CSRF, and CORS deliberately.

## Vanilla compatibility

The implementation relies only on endpoints shipped by GeoNode 5.1.0:

- [`account/ajax_login`](https://github.com/GeoNode/geonode/blob/5.1.0/geonode/views.py) creates the Django session.
- [GeoNode URL configuration](https://github.com/GeoNode/geonode/blob/5.1.0/geonode/urls.py) exposes login, logout, and API V2 routes.
- [The API V2 user viewset](https://github.com/GeoNode/geonode/blob/5.1.0/geonode/people/api/views.py) requires authentication and returns the user profile.
- [The API V2 user-info view](https://github.com/GeoNode/geonode/blob/5.1.0/geonode/api/views.py) identifies the current Django session after password or social login.
- [The API V2 user serializer](https://github.com/GeoNode/geonode/blob/5.1.0/geonode/people/api/serializers.py) defines the mapped profile fields.

No GeoNode setting, view, middleware, authentication backend, or database model is replaced by Mirante.
